# Research: Update LLM Service Layer & Protocols for Generation Parameters

**Date**: 2026-03-18

## 1. Executive Summary
The goal is to update the LLM service layer and its protocols to support generation parameters (temperature, max tokens, top-p, etc.). Currently, these parameters are defined in `LLMConfiguration` and `ProviderConfiguration` but are not passed down through the `LLMServiceProtocol` and `LLMClientProtocol` to the actual client implementations (`OpenAIClient`, `OllamaClient`, `OpenRouterClient`).

## 2. Technical Context
- **`LLMServiceProtocol`**: Located at `Sources/MonadCore/Services/LLM/LLMServiceProtocol.swift`. Defines `chatStream` and `sendMessage` methods.
- **`LLMClientProtocol`**: Defined in `Sources/MonadCore/Services/LLM/LLMService.swift`. Used by `LLMService` to interact with different providers.
- **`LLMService`**: Located at `Sources/MonadCore/Services/LLM/LLMService.swift`. Implements `LLMServiceProtocol` and manages client switching.
- **`LLMConfiguration`**: Located at `Sources/MonadShared/SharedTypes/LLMConfiguration.swift`. Contains the flat structure of generation parameters which are mapped to the active provider.
- **`ProviderConfiguration`**: Located at `Sources/MonadShared/SharedTypes/ProviderConfiguration.swift`. Actually stores the parameters per provider.
- **`UnconfiguredLLMService`**: Located at `Sources/MonadCore/Dependencies/LLMDependencies.swift`. A placeholder implementation that must match the protocol.

### Existing Parameters in `ProviderConfiguration`
- `temperature: Double?`
- `maxTokens: Int?`
- `topP: Double?`
- `frequencyPenalty: Double?`
- `presencePenalty: Double?`

## 3. Findings & Analysis
- **Missing Transmission**: `LLMChatRequest` and the `chatStream`/`sendMessage` methods in both `LLMServiceProtocol` and `LLMClientProtocol` do not take these parameters as arguments.
- **OpenAI Integration**: `OpenAIClient` uses the `ChatQuery` struct from the `OpenAI` package, which already supports these parameters. They just need to be passed in.
- **Ollama Integration**: `OllamaClient` builds its own `OllamaChatRequest`. It needs to be updated to include an `options` dictionary/struct to support these parameters.
- **OpenRouter Integration**: `OpenRouterClient` also uses `ChatQuery` but encodes it manually. It will automatically benefit from `ChatQuery` updates if they are passed to the initializer.
- **Service Logic**: `LLMService` needs to extract these parameters from its current `configuration` and pass them to the client.

## 4. Technical Constraints
- **Protocol Stability**: Changing the protocol requires updating all conformers, including mocks and placeholders.
- **Backward Compatibility**: `LLMConfiguration` and `ProviderConfiguration` are `Codable`. Changes to their structure might affect persisted settings if not handled carefully with `CodingKeys`.
- **OpenAI Dependency**: The project relies on `MacPaw/OpenAI`. The types used must be compatible with `ChatQuery`.

## 5. Architecture Documentation
- The project follows a service-client architecture. `LLMService` acts as a facade/coordinator, and `LLMClientProtocol` provides provider-specific implementations.
- Configuration is centralized in `MonadShared` and injected into the service.
- `LLMChatRequest` is the primary high-level request object used by the `ChatEngine`.
